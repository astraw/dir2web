# Contributing to dir2web

## Checks

CI runs these; run them before committing:

```sh
cargo fmt
cargo clippy --all-targets -- -D warnings  # warnings are treated as errors
cargo test
```

`tests/browser/play.mjs` and `tests/browser/model.mjs` exercise the video
player and the 3D model viewer in real browsers; see the README. Run them
after changing either.

## Commit messages

Commits must follow the [Conventional Commits](https://www.conventionalcommits.org)
specification — release automation derives version bumps and the changelog
from them. Use a type prefix and an imperative summary:

```
feat: render README.md below directory listings
fix: report evicted previews as missing
docs: describe the cache limit
```

Common types: `feat`, `fix`, `docs`, `refactor`, `test`, `chore`, `ci`.
Mark breaking changes with `!` (`feat!: ...`) or a `BREAKING CHANGE:` footer.

## Third-party licenses

`THIRD-PARTY-LICENSES` collects the license texts of the dependencies compiled
into dir2web; it is bundled into every release archive. If you add, remove, or
upgrade a dependency, regenerate it:

```sh
cargo bundle-licenses --format yaml --prefer MIT --previous THIRD-PARTY-LICENSES --output THIRD-PARTY-LICENSES
cat static/THIRD-PARTY-LICENSES.yaml >> THIRD-PARTY-LICENSES
```

`--previous` carries over license texts that were filled in by hand because
the published crate ships none (currently `valuable`, whose text is from
upstream's `LICENSE` at the matching tag). If the output contains
`NOT FOUND` for another crate, fill it in the same way; CI rejects the file
otherwise.

The second line appends `static/THIRD-PARTY-LICENSES.yaml`, the
hand-maintained entries for the JavaScript and WebAssembly files embedded
from `static/` (such as hls.js): they are not Cargo dependencies, so the
generator cannot see them. When adding or upgrading one of those files,
update its entry there. CI checks that `THIRD-PARTY-LICENSES` ends with it.

## Releasing

Releases are automated with [release-plz](https://release-plz.dev) and
[cargo-dist](https://axodotdev.github.io/cargo-dist/):

1. Every push to `main` makes release-plz open (or update) a release PR that
   bumps the version from the Conventional Commits since the last release and
   updates `CHANGELOG.md` (generated by [git-cliff](https://git-cliff.org)
   with `cliff.toml`).
2. Merging that PR makes release-plz publish the crate to crates.io and push
   a `vX.Y.Z` tag. Other pushes to `main` release nothing
   (`release_always = false`).
3. The release-plz workflow then dispatches the cargo-dist workflow
   (`.github/workflows/release.yml`) for that tag, which builds the binaries
   and creates the GitHub release with them and the installer script
   attached. To redo a release's binaries, run that workflow by hand from the
   Actions tab with the tag as input.

`release.yml` is generated: after changing `dist-workspace.toml` or upgrading
cargo-dist, run `dist generate` instead of editing it by hand.

No long-lived credentials are stored on GitHub. crates.io is published to
with [trusted publishing](https://crates.io/docs/trusted-publishing), and the
workflows otherwise only use the built-in `GITHUB_TOKEN`.

One-time setup:

- GitHub, Settings → Actions → General → Workflow permissions: allow GitHub
  Actions to create and approve pull requests (for the release PR).
- GitHub, Settings → Environments: an environment named `release`,
  restricted to deployments from the `main` branch (and, optionally, with
  required reviewers, which makes each release wait for an approval). The
  publishing job runs in it; a `release-check` job first makes sure only
  merges of release PRs get there.
- crates.io, the crate's Settings → Trusted Publishing: add GitHub owner
  `astraw`, repository `dir2web`, workflow `release-plz.yml`, environment
  `release`. (crates.io cannot do this before a crate exists; v0.1.0 was
  published with a one-off API token.)
